# 写作与核查 skill

## 四条判据

1. **只写“换个项目仍成立”的内容。** 一次性事实——条目 id、绝对路径、某次发布的字节数、当前订阅了哪些前置、某台机器上的版本号——不进 skill，进项目文档（`docs/`、`PROGRESS.md`）。判断法：把这段文字搬到另一个仓库，它还成立吗？
2. **能力，不是叙事。** 进 skill 的是“下次怎么做”和“哪里会炸”，不是“我们上次怎么解决的”。调试流水账删掉，只留结论与陷阱。
3. **环境假设显式。** 依赖哪个 CLI、哪个版本、缺了怎么降级，写在被依赖的那一步旁边。反例：某官方 skill 的评测段要求 `Codex -p`，本机没有，读者只能自己踩到才发现。
4. **冲突要有裁决。** 同名 skill 在运行时是“列表里第一个命中胜出”，不报错；同类不同名则两份都可能被读到。所以文本里要写清“按 A 而不按 B，因为 …”。

## 30 秒流程

1. 定能力：一句话说清“什么时候用、给出什么”，并举 2–3 个用户真实会说的话作为触发句。
2. 搜现有：目标目录里是否已有同能力 skill？有就改它——`name` 与目录名不变，description 只加触发词、不减。
3. 分资源：正文留判据与流程；精确规格 → `references/`；脆弱、多步、要算准的 → `scripts/`；逐字复用的模板 → `assets/`。
4. 先写 description（见下节），再写正文。
5. 跑校验：`python scripts/check_skill.py <skill-dir>`（本机 Python 3.12，无第三方依赖）。
6. 干跑：拿第 1 步的触发句，确认读完正文能否直接执行；不能就补步骤，不要补形容词。

## description 怎么写

唯一作用：让读者判断“现在要不要读这份技能”。

- 句式：`用于 <做什么>。当用户说“<触发句 1>”“<触发句 2>”…时使用。` 第三人称，不写“我可以帮你…”。
- **只写触发条件，不概括正文流程。** 这是实测结论：描述里概括了流程，模型会照描述做而不去读正文（例：描述写“任务间做代码审查”，模型只做了一次审查，而正文要求两次）。来源：obra/superpowers 的 `writing-skills`（SDO 节）。
- 触发词写具体症状与场景，不写实现细节；技能是技术特定的就明说，不特定就别塞技术名词。
- 长度：一到三句，60–200 字符最常见；1024 字符是规格上限，不是目标。

## 目录与体积

```
<skill-name>/
├── SKILL.md            必需：frontmatter + 判据与流程
├── references/         精确规格、表格、判定边界
├── scripts/            需要每次结果一致的操作
└── assets/             逐字复用的模板、字体、图
```

- `SKILL.md` 目标 ≤ 150 行；超了拆到 `references/`，正文留一句“何时读它”。
- 不放 `README.md` / `CHANGELOG.md` / `INSTALLATION.md`：那是给维护者的，不是给执行者的。
- 同一事实只写一处；需要两处就一处为准、另一处指过去。

## 环境与能力假设（本机实测，2026-11）

| 能力 | 本机状态 | 写 skill 时怎么处理 |
|---|---|---|
| Node / npm | v24.12.0 / 11.8.0 | 可直接依赖 |
| Python | 3.12.11，命令是 `python`，**没有** `py` | 可直接依赖 |
| `Codex` CLI | 不存在 | 不要假设；需要就写前置 |
| 技能根 | `dsh-packs/pack-test/skills/`（随包分发）、`C:\Users\<user>\.agents\skills`（用户级） | 两者都按目录扫描，写入后下一轮即可加载，无需重启 |
| 选择机制 | 目录常驻 name+description，正文按需加载；同名先命中者胜 | 冲突只能靠文本裁决 |

## 同名与冲突

- **同名**：加载器是 `list().find(s => s.name === args.name)`，第一个命中胜出且静默。改名会破坏引用，不要靠改名“解决”冲突。
- **同类不同名**：两份都可能被读到，给出相反做法时没有运行时仲裁。在正文里写“与 X 冲突时以本文为准 / 以 X 为准”，并给理由。
- **合并优于复制**：覆盖同一能力时保留触发面更广的一份，另一份改成一行指针。

## 核查别人写的 skill

只看文本、不改文件，按序检查：

1. 混入一次性事实（绝对路径、条目 id、字节数、本机版本）？
2. description 概括了流程，而不是只给触发条件？
3. 把“上次怎么解决的”当成能力写进去？
4. 依赖的 CLI/工具是否存在，缺失时有前置或降级说明？
5. `SKILL.md` 超过 150 行且没有 `references/` 兜底？
6. 断链（引用的相对路径不存在）或与相邻 skill 触发面重叠？
7. 触发词覆盖用户真实说法（中文口语、错误形状），而不只是术语？

报告形态：每条给 `文件:行号`、问题、后果、一条修法。判定标准与严重度见 `references/audit-checklist.md`。

## 校验脚本

```bash
python scripts/check_skill.py <skill-dir>          # 单个技能
python scripts/check_skill.py --all <skills-dir>   # 整个技能目录
```

检查项：frontmatter 的 `name`/`description`、名字与目录同名且 kebab-case、description 长度与第一人称、正文行数、技能目录内的 README/CHANGELOG、相对链接断链、正文里的绝对路径。退出码 1 表示存在 error。

## 不要做

- 不要用 skill 存“这次任务的过程”。
- 不要把同一条规则同时写在 SKILL.md 与 references（会分叉）。
- 不要为了显得正式而堆 MUST/ALWAYS：解释“为什么”比加强断言更稳。
- 不要宣称跑过一个实际没跑的命令。
